# 06. Reference Analysis

> Winter Dev Archive 디자인의 기준 문서.  
> 두 레퍼런스의 설계 철학을 분석하고, 이 프로젝트만의 방향을 정의한다.

---

## 프로젝트 목표

Winter Dev Archive는 다음 두 가지 목표를 동시에 달성해야 한다.

1. **교안 사이트로서의 기능성** — 학습 콘텐츠를 빠르게 찾고, 읽고, 참고할 수 있어야 한다
2. **아카이브로서의 정체성** — 누군가의 공부 노트처럼 따뜻하고 개인적인 느낌이 있어야 한다

이 두 목표를 동시에 충족하는 디자인 방향을 찾기 위해 아래 두 사이트를 분석한다.

## 레퍼런스 1 분석 — 강사님 교안 사이트

> `https://hw5511.github.io/vibe-web/`  
> AI 바이브 코딩 강의 교안 사이트 (React 기반 커스텀 docs 사이트)

### 사이트 구조 파악

스크린샷 기준으로 확인한 실제 레이아웃:

```
┌──────────────────────────────────────────────────────┐
│  Vibe Web   Setup  Lesson 1  Lesson 2  Lesson 3  Lesson 4  │  ← 상단 GNB
├──────────────┬───────────────────────────────────────┤
│  Setup       │  1단계: 개발환경 구축                  │
│              │                                       │
│  1단계: 개발  │  Windows 또는 Mac에서 Git, Node.js,  │
│  환경 구축 ▾  │  Claude Code를 설치하여 AI 기반 웹  │
│   Windows    │  개발 환경을 완성합니다.               │
│   Mac        │                                       │
│   VSCode     │  ┌─────────────────────────────────┐  │
│              │  │ 💡 이 단계에서 설치할 도구      │  │  ← callout
│  2단계 >     │  │   Git / Node.js / Claude Code   │  │
│  3단계 >     │  └─────────────────────────────────┘  │
│  4단계 >     │                                       │
│  5단계 >     │  Windows 설치 가이드                  │
└──────────────┴───────────────────────────────────────┘
```

### 좋은 점

| 항목                     | 내용                                                                           |
| ------------------------ | ------------------------------------------------------------------------------ |
| **3단계 레이아웃**       | 상단 GNB(대단원) + 좌측 사이드바(소단원) + 본문의 3단 구조가 명확              |
| **명확한 학습 경로**     | Setup → Lesson 1 → 2 → 3 → 4, 단계를 숫자로 명시해 전체 커리큘럼이 즉시 파악됨 |
| **접기/펼치기 사이드바** | 현재 단계의 하위 항목만 펼쳐지는 accordion 방식 — 탐색 부담이 낮음             |
| **callout 박스 활용**    | 아이콘 + 테두리 색으로 보조 정보를 본문과 시각적으로 분리                      |
| **콘텐츠 집중 설계**     | 불필요한 장식 없이 학습 내용 자체에 집중할 수 있는 구조                        |
| **일관된 단계 표기**     | `1단계`, `2단계` 형식이 전체 사이트에서 통일되어 있음                          |

### 가져올 요소

- **GNB + 사이드바 이중 탐색 구조** — 큰 섹션은 상단으로, 세부 문서는 좌측으로
- **accordion 사이드바** — 현재 위치의 하위 항목만 펼쳐 탐색 부담 최소화
- **번호 기반 문서 체계** — 단원 번호 + 하위 항목 번호로 전체 구조를 숫자로 표현
- **callout 박스 형태** — 아이콘 + 좌측 accent bar 방식의 정보 강조
- **콘텐츠 우선 레이아웃** — 탐색 UI가 본문 읽기를 방해하지 않는 비율

### 가져오지 않을 요소

| 요소                  | 이유                                                                      |
| --------------------- | ------------------------------------------------------------------------- |
| 순백 배경 (`#FFFFFF`) | 장시간 읽기에 눈이 피로하다. 크림화이트(`#FAF8F5`)로 대체                 |
| 무채색 단일 포인트    | 파란 callout 하나 외에 포인트 컬러 체계가 없다. 보라 팔레트로 정체성 부여 |
| 캐릭터/감성 요소 없음 | 기능적이지만 개인 아카이브의 따뜻한 정체성이 없다                         |
| 다크 모드 없음        | 야간 학습 환경을 고려해 딥 퍼플 잉크 다크 모드 지원 필요                  |
| 섹션 간 연결 없음     | 현재 문서에서 관련 다른 섹션으로 연결하는 크로스 링크가 없다              |

- **개인 아카이브 감성** — 사이트가 만든 사람의 성격을 담아야 한다는 방향성

| 요소                     | 이유                                                                               |

| WebGL 기반 인터랙션      | 학습 중 주의가 분산된다. 교안 사이트에서 과도한 인터랙션은 콘텐츠를 방해           |
| 포트폴리오 중심 레이아웃 | 작업 전시 구조는 문서 참조 구조와 다르다                                           |
| 무거운 애니메이션        | 빠른 페이지 전환과 정보 탐색이 우선인 아카이브에서는 역효과                        |
| 이미지 중심 카드         | 텍스트 중심의 학습 문서에서 이미지 썸네일은 오히려 정보를 가린다                   |

## 두 레퍼런스 비교 분석

### 공통점

- 둘 다 **흰색보다 따뜻한 배경**을 사용한다 (Notion 크림화이트 / Yan Liu `#FAF8F5`)
- 과도한 장식보다 **콘텐츠 자체의 품질**을 신뢰하는 설계 방향
- 방문자가 **길을 잃지 않도록** 구조가 명확하다

### 차이점

| 항목        | 강사님 교안 사이트                  | Yan Liu Portfolio          |
| ----------- | ----------------------------------- | -------------------------- |
| 주목적      | 정보 전달 / 학습 경로 안내          | 자기 표현 / 작업 전시      |
| 구조        | 계층형 (Setup > Lesson > 세부 항목) | 선형 (스크롤 스토리텔링)   |
| 인터랙션    | 최소화 (클릭 이동)                  | 극대화 (애니메이션, WebGL) |
| 개인성      | 낮음 (기능 중심)                    | 높음 (감성 중심)           |
| 재방문 목적 | 정보 재참조                         | 인상 재경험                |
| 장기 사용   | 적합 (빠른 탐색)                    | 부적합 (첫 인상용)         |

### 각각의 강점

**강사님 교안 사이트 강점**

- 학습자가 어디에 있는지 항상 인지할 수 있는 명확한 경로
- 레슨 번호 체계로 전체 커리큘럼이 머릿속에 잡힌다
- 군더더기 없이 학습 내용에 집중할 수 있는 구조

**Yan Liu Portfolio 강점**

- 사이트 자체가 하나의 경험이 되는 설계
- 색상 톤의 통일감이 만들어내는 브랜드 일관성
- 따뜻하고 개인적인 느낌이 신뢰감을 형성

### 각각의 약점

**강사님 교안 사이트 약점**

- 순백 배경과 무채색 포인트 — 사이트 고유의 색상 정체성이 없다
- 캐릭터·감성 요소 부재 — 기능적이지만 "누구의 아카이브"인지 느껴지지 않는다
- 다크 모드 미지원
- 섹션 간 크로스 링크 없음 — 관련 문서 탐색이 단절됨

**Yan Liu Portfolio 약점**

- 정보 탐색이 목적인 사용자에게는 불편하다
- 재방문 시 모든 애니메이션을 다시 기다려야 한다
- 교안·문서 사이트에 적용하기 어려운 구조

### 왜 그렇게 결정했는가

Winter Dev Archive의 핵심 사용 패턴은 **"나중에 다시 찾아오는 것"** 이다.  
처음 방문의 인상보다 **열 번째 방문에도 빠르게 원하는 것을 찾는 경험**이 더 중요하다.

따라서:

- **구조는 교안 사이트에서** — 반복 방문과 빠른 탐색에 최적화된 계층 구조
- **감성은 Yan Liu에서** — 크림 배경과 색온도 통일로 오래 봐도 질리지 않는 분위기
- **정체성은 Winter 본인에게서** — 보라 잉크 + 다꾸 감성으로 누가 만든 아카이브인지 느껴지도록

## 금지할 디자인 요소

### 시각적 요소

- **과도한 애니메이션** — 페이지 전환, 스크롤 효과, 요소 등장 애니메이션 모두 최소화
- **과도한 그림자** — box-shadow는 드롭다운과 모달에만 제한적으로 사용
- **그라데이션 배경** — 크림 배경의 통일감을 깨뜨림
- **이미지 썸네일 카드** — 텍스트 문서 목록에서 불필요
- **밝은 원색 포인트 컬러** — 팔레트 외부의 색상 사용 금지 (오렌지, 초록, 빨강 등)
- **큰 Hero 이미지 섹션** — 교안 사이트에서 대형 배너는 공간 낭비
- **sticky 광고형 CTA** — 학습 흐름을 방해하는 플로팅 요소

### 레이아웃 요소

- **단일 페이지 스크롤 구조** — 문서가 많은 아카이브에 맞지 않음
- **무한 스크롤** — 끝이 있어야 탐색 완료 감이 생긴다
- **카드에 과도한 정보 밀어넣기** — 제목 + 설명 + 날짜면 충분
- **3단 이상의 레이아웃** — 사이드바 + 본문 + 우측 패널은 과하다

### 텍스트 요소

- **문단 들여쓰기** — 기술 문서에서는 여백으로 단락 구분
- **정렬되지 않은 텍스트** (justified) — 가독성 저해
- **지나치게 작은 폰트** — 12px 미만 사용 금지
- **배경색과 명도 차이가 작은 텍스트** — `ink-300` 이하 단독 사용 금지

## 최종 디자인 컨셉

### 한 문장

> **"크림 노트에 보라 잉크로 필기한 디지털 참고서"**

### 짧은 문단

교안의 명확함과 노트의 따뜻함을 동시에 갖춘 학습 아카이브.  
빠르게 찾고, 편하게 읽고, 다시 꺼내보고 싶은 사이트.

### 상세 설명

Winter Dev Archive는 한 사람의 프론트엔드 학습 여정을 담은 개인 아카이브다.  
기술 블로그처럼 날짜로 읽는 것이 아니라, 교과서처럼 주제로 찾아보는 방식으로 설계된다.

디자인은 화려함보다 **지속 가능한 가독성**을 택한다.  
크림화이트 배경은 종이를 연상시키고, 더스티 바이올렛 포인트는 잉크처럼 자연스럽게 스며든다.  
구조는 강사님의 교안 사이트처럼 계층이 명확하되, 색상과 타이포그래피는 Yan Liu의 크림 감성을 계승한다.

무엇보다 이 사이트는 **Winter 본인이 두고두고 꺼내볼 참고서**다.  
그래서 처음 방문자의 감탄보다, 열 번째 방문에도 바로 찾을 수 있는 구조가 우선이다.

## 캐릭터 활용 전략

### 캐릭터를 사용하는 이유

Winter Dev Archive는 단순한 문서 사이트가 아니라 **한 사람의 학습 여정을 담은 개인 아카이브**다.  
겨울하음 캐릭터는 이 사이트가 "누군가의 것"임을 느끼게 해주는 가장 직접적인 수단이다.

두 레퍼런스와 비교했을 때:

| 사이트                 | 개인성 표현 방식                                  |
| ---------------------- | ------------------------------------------------- |
| 강사님 교안 사이트     | 없음 — 기능 중심, 누구의 것인지 느껴지지 않음     |
| Yan Liu Portfolio      | 드로잉·사진으로 작가 정체성을 직접 표현           |
| **Winter Dev Archive** | 캐릭터로 아카이브 주인의 존재감을 간접적으로 표현 |

캐릭터는 사이트의 **감성 레이어**다.  
콘텐츠를 대체하거나 경쟁하지 않고, 학습 경험의 특정 순간에만 등장해 따뜻함을 더한다.

---

### 캐릭터 사용 원칙

1. **콘텐츠가 먼저, 캐릭터는 나중** — 캐릭터는 학습 내용보다 앞에 서지 않는다
2. **기능적 맥락에만 등장** — 장식을 위한 배치는 하지 않는다. 캐릭터가 "의미 있는 순간"에만 나온다
3. **크기는 작게, 위치는 주변부** — 본문 읽기 영역을 침범하지 않는다
4. **감정 표현은 상황에 맞게** — 완료 시 기쁨, 오류 시 당황, 빈 화면 시 안내 등 맥락에 따른 표정/포즈
5. **반복 노출을 피한다** — 한 화면에 캐릭터가 두 곳 이상 나오지 않는다
6. **애니메이션은 최소화** — idle 애니메이션이 있더라도 매우 subtle하게, 학습 중 시선을 빼앗지 않도록

---

### 과도한 사용을 금지하는 이유

캐릭터를 여러 곳에 배치하면 다음 문제가 발생한다.

| 문제                 | 설명                                               |
| -------------------- | -------------------------------------------------- |
| **학습 집중도 저해** | 읽는 도중 캐릭터가 시야에 들어오면 주의가 분산된다 |
| **전문성 하락**      | 학습 참고서보다 키즈 앱처럼 보일 수 있다           |
| **감성이 희석됨**    | 자주 보이면 특별함이 사라진다. 희소해야 의미 있다  |
| **레이아웃 오염**    | 캐릭터 공간을 확보하느라 정보 배치가 왜곡된다      |

---

### 사용 위치

캐릭터가 등장하는 곳은 **학습 흐름의 전환점** 또는 **비어있는 공간**으로 한정한다.

| 위치                  | 상황                              | 캐릭터 역할                                               |
| --------------------- | --------------------------------- | --------------------------------------------------------- |
| **Home 페이지**       | 첫 방문 또는 복귀 시              | 사이트 소개, 따뜻한 진입점 역할. 우측 하단 또는 Hero 영역 |
| **Empty State**       | 검색 결과 없음, 빈 카테고리       | "아직 내용이 없어요" 안내. 캐릭터 + 짧은 문구             |
| **학습 완료 화면**    | 문서 status = `completed` 처리 시 | 소소한 축하. 캐릭터 + "잘했어!" 같은 짧은 메시지          |
| **404 / 오류 페이지** | 잘못된 URL 접근                   | 당황한 표정 + "이 페이지는 없어요" 안내                   |
| **About 페이지**      | 사이트 소개 섹션                  | 자기소개 역할. 가장 크고 자유롭게 사용 가능               |

---

### 사용하지 않을 위치

| 위치                   | 이유                                                            |
| ---------------------- | --------------------------------------------------------------- |
| **문서 본문 영역**     | 읽기 흐름을 방해한다. 텍스트와 캐릭터가 섞이면 집중이 깨진다    |
| **코드 블록**          | 코드 옆 캐릭터는 전문성을 낮추고 공간을 낭비한다                |
| **사이드바 탐색 영역** | 탐색 UI에 캐릭터가 있으면 탐색 자체에 방해가 된다               |
| **카드 목록**          | 콘텐츠 카드 내부에 캐릭터를 넣으면 정보 밀도와 정렬이 무너진다  |
| **헤더 / 푸터**        | 모든 페이지에 고정 노출되므로 반복 노출 문제가 생긴다           |
| **Callout 박스**       | Callout은 정보 강조 컴포넌트다. 캐릭터를 넣으면 의미가 희석된다 |
| **로딩 스피너 대체**   | 로딩 중 캐릭터 애니메이션은 성능 체감을 나쁘게 만든다           |

---

### 캐릭터 사용 빈도 요약

```
많이 사용  ← ─────────────────────────────── → 절대 사용 금지
  About     Home    Empty   완료 화면   본문 / 사이드바 / 코드블록
  페이지     진입    State   (간헐적)    탐색 영역 / 카드 목록
```

한 방문 세션에서 캐릭터를 보는 횟수: **최대 2회** 이내를 목표로 한다.  
캐릭터는 자주 보이는 친구가 아니라, 가끔 만나는 반가운 존재여야 한다.
